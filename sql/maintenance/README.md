# Исправление контрактов истории после аудита L50–L59

Эта процедура нужна существующему стенду редакции 2.0. Чистый стенд сразу создаёт новые структуры. Выполняйте миграцию в отдельном окне без параллельной генерации и публикации отчётов.

1. Сохраните код и контрольные суммы, результат reconciliation, количества источников. Остановите автоматические загрузки на время процедуры.
2. Обновите определения функций из `sql/01_generator.sql` через PostgreSQL-контейнер. Само применение файла не вызывает `seed_history` или `simulate_day`.
3. Примените `repair_source_contracts.sql`. В одной транзакции он архивирует изменяемые поля заказов и полные изменяемые записи возвратов в `meta.course_repair_l51/l52`, затем чинит watermark и ограничивает суммарный возврат количеством покупки. Самые ранние возвраты сохраняются первыми; последним частичным возвратам корректируется количество и пропорциональная сумма. Это исправление ошибочных синтетических данных, а не универсальная политика для финансового источника.
4. Примените `recreate_vault_history.sql` через StarRocks. Меняется схема пяти производных спутников; они будут восстановлены из bronze. После DROP до создания таблиц не обращайтесь к ним через SELECT/SHOW CREATE.
5. Запустите полный dbt build с `--vars '{reload_from_date: "1970-01-01"}'`. Нужен весь DAG: обе bronze, все staging и ядра, все витрины. Не используйте `--full-refresh` для внешних incremental-таблиц.
6. Проверьте агрегированный source-контракт возвратов, полноту текущего переноса возвратов, watermark, все тесты и `make reconcile`. Повторите обычный build: число наблюдённых mutable-версий и время их первой загрузки должны сохраниться.

Архивные таблицы не удаляются процедурой. Для отката источника используйте сохранённые строки и прежние значения `updated_at` в отдельном окне; после отката требуется согласованно восстановить downstream. Слепое восстановление архива поверх последующих новых изменений недопустимо. Потерянные до внедрения сохраняемой bronze версии этот ремонт восстановить не может.
