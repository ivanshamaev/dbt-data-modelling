# Сравнение трёх канонических витрин пяти контуров

Текущий `make bench` запускает 15 запросов из [canonical](canonical/):
`sales_daily`, `customer_ltv`, `promo_effect` для Inmon, Kimball, Vault, Anchor и Medallion.
В пределах одной витрины совпадают колонки, зерно, меры и сортировка. Набор прежних
`bench_kpi*.sql` оставлен как исторический материал и в текущем измерении не используется.

## Зафиксированный протокол

1. Остановить генерацию дней и другие сборки. Зафиксировать версии, ресурсы стенда,
   журнал источника, ревизию файлов и успешный полный build.
2. Проверить R1–R4 до измерения. Отсутствующая секция или FAIL останавливает команду.
3. Для каждой пары витрина/контур сохранить EXPLAIN и хеш SQL, выполнить один прогрев.
4. Выполнить пять последовательных запросов, сохранить каждый интервал в микросекундах.
5. Опубликовать третье значение отсортированного набора — медиану пяти замеров, в мс.
6. Сравнить маркер источника до/после и повторить R1–R4. Маркер не является полным
   хешем всех исходных таблиц; отсутствие иных писателей — условие эксперимента.

Измеряется **wall-clock вызова клиента через Compose**: запуск клиента, SQL,
передача и форматирование результата. `> /dev/null` убирает показ строк пользователю,
но не удаляет эти затраты из измерения. Называть это чистым временем движка нельзя.
EXPLAIN показывает план и оценки; он не заменяет фактический профиль scan rows/bytes.
Кэши не сбрасываются. Порядок фиксирован в `run.sh`, поэтому результаты не являются
рандомизированным сравнением и не описывают холодный старт.

По умолчанию артефакты создаются в новом каталоге `run-<UTC-время>` рядом с этим
README; `OUT` позволяет задать каталог сессии. Сохраняются все 75 интервалов,
15 планов, хеши запросов, маркеры источника и две сверки. Не подменять новые замеры
старым `results.md` без даты и условий. Курсовая сессия сохраняет результат в
`docs/live-run/course-final-2026-10-31/`.

## Сборки и потребление ресурсов

`bash scripts/measure_contours.sh` последовательно запускает пять штатных целей
Make. Для каждого контура сохраняются три предварительных семпла и семплы
`docker stats` во время сборки, полный лог и `run_results.json`. Измеряется **один
повтор на неизменном источнике**, а не медиана первой загрузки и не стоимость
произвольного нового дня. Для первых четырёх команд включён общий bronze.

CPU/RAM — сумма пяти основных контейнеров во время одной активной сборки.
100% CPU в Docker соответствует одному ядру; публикуются среднее семплов и
максимальный семпл. RAM отражает трактовку Docker CLI для Linux, которая вычитает
inactive file cache; это не полный расход памяти всего узла. Фоновые компакции
и служебная работа контейнеров остаются внутри измерения. См. [Docker stats](https://docs.docker.com/reference/cli/docker/container/stats/).

`make resources` собирает другой набор величин: PostgreSQL с индексами/TOAST,
текущие файлы Iceberg через `$files`, все объекты активных UUID-префиксов S3,
внутренние таблицы через SHOW DATA и модели/тесты через manifest. Текущие файлы
и сохранённые старые snapshots показываются раздельно. Немаппированные префиксы,
включая старые объекты и сценарные пространства, не приписываются методологиям.
[Метаданные Iceberg в StarRocks](https://docs.starrocks.io/docs/data_source/catalog/iceberg/iceberg_meta_table/)
описывают, что именно содержит `$files`.

## Как интерпретировать результат

Размер PostgreSQL с индексами нельзя напрямую сравнивать с одним сжатым Parquet
как оценку эффективности модели. Четыре контура разделяют инжест, Medallion имеет
свой. Kimball использует internal StarRocks, остальные ядра — Iceberg; это
физическое различие входит в замер. У ядер разный состав истории и вспомогательных
структур. Равенство трёх витрин подтверждает только согласованные вопросы.

Числа пригодны для обсуждения конкретного стенда, данных и алгоритмов загрузки.
Для общего вывода нужны другие объёмы, сценарии изменений, повторные серии,
контроль фоновой нагрузки и цена сопровождения. Отсутствующие измерения
обозначаются как отсутствующие, а не заполняются нулями или «типичными» числами.
